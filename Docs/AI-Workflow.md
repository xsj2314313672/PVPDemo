# PVPDemo AI 协作流程

本文档是「协作流程」维度的唯一来源，描述 AI 在项目中的读取顺序、文档同步判定与输出要求。代码规范与资产规范分别见 `Docs/Source-Structure.md`、`Docs/Content-Structure.md`，本文不重复。

> **上下文入口**：根目录 `AGENTS.md` 提供项目定位、`Docs/` 文档地图与硬约束，客户端支持时于会话开始时自动加载（前提是项目根不存在 `CODEBUDDY.md`）。为防止新会话漏读，`.codebuddy/rules/doc-first/RULE.mdc` 以 `alwaysApply: true` 常驻，只承担「先读 `AGENTS.md`，再按维度拉取 `Docs/`」的导航，**不承载规范正文**；规范仍以本仓库文档为唯一来源。

---

## 1. 每次任务开始前

1. **定位维度**：按 `AGENTS.md` 的文档地图判断本次改动属于源码、资产、模块还是流程/文档维度，只拉取对应文档。
2. **模块优先走导航**：改动涉及某个功能模块（如 Input、Camera、GAS、Equipment）时，先读 `Docs/<模块>/README.md`，再由导航的「文档清单与路由」决定读 `<模块>-Dev.md`、`<模块>-Integration.md` 的哪几节。仅当导航未覆盖、文档与代码疑似不一致，或需要精确签名时，才用 `search_content` / 精准 `read_file` 定点核对；**禁止为"熟悉模块"而整目录通读源码或资产**。
3. **按需读取**：只读与本次改动相关的章节；单个文档超过约 500 行时，先读标题结构再精读相关章节。禁止只看文件名或凭经验推测规范。
4. **复述约束**：用 1～3 行说明本次改动要遵守的关键约束（所属目录、命名前缀、阶段限制、依赖方向），确认与 Docs 无冲突。
5. **冲突处理**：Docs 未覆盖或与需求冲突时，先说明冲突点并以 Docs 为准；确需突破规范时，必须显式标注"拟偏离 Docs 的 X 条，理由为……"，等用户确认后再动手，禁止自行发明规范。
6. **再动手**：完成第 1～5 步后才生成或修改代码 / 资产 / 文档。

## 2. "必须同步文档"的判定标准

出现以下任一项即需同步文档，不得只改代码：

- **增量**：新增文件 / 目录 / 类 / 资产 / 模块 / 依赖，或出现新的命名前缀。
- **删减**：删除、重命名、移动、合并文件或资产。
- **结构变化**：任一目录内的数量发生变化，或某占位目录由"空 / 预留"变为"已实现"。
- **模块首次实现**：功能模块（源码分层或逻辑资产模块）由"预留 / 空"进入实现阶段时，必须建立 `Docs/<模块>/` 并产出固定三件套（见第 6 节）。
- **模块契约变化**：已有模块的对外接口、依赖方向、数据流、资产契约或已实现动作 / 绑定关系发生变化时，同轮更新该模块导航的能力速查表与 `<模块>-Integration.md`。
- **新增踩坑**：开发中出现需要后来者规避的问题（方向错、顺序错、资产需重建等）时，当轮追加到 `<模块>-Dev.md` 的踩坑清单，不得只留在会话上下文里。

## 3. 文档同步清单（逐项核对）

| 文档 | 需要同步的内容 |
| --- | --- |
| `Docs/Content-Structure.md` | 第 1 节目录树及数量、第 2 节命名前缀对照（出现新前缀时）、第 3 节各模块表格与子文件夹说明、文首"当前状态"的资产总数 |
| `Docs/Source-Structure.md` | 第 1 节目录树、第 2 节各模块的规划文件 / 职责 / 阶段表格、文首"当前状态"与"阶段说明"（目录由空变实、功能由预留变实现时必须改写） |
| `Docs/<模块>/README.md` | 模块定位与边界、文档清单与路由、已实现能力速查表、启动与校验入口；新增 / 修改 / 删除本模块文档时必须同步（见第 6 节） |
| `Docs/<模块>/<模块>-Dev.md` | 范围与当前状态、源码结构、设计决策、开发 SOP、踩坑清单、校验与冒烟、已知限制；实现变化或出现新踩坑时同步 |
| `Docs/<模块>/<模块>-Integration.md` | 模块依赖、数据流与交互、对外接口、其他模块调用方式、禁止依赖方向、变更影响面；接口或依赖变化时同步 |
| `Docs/AI-Workflow.md` | 仅当协作流程本身变化时 |
| `AGENTS.md` | 新增 / 改名 / 删除 `Docs/` 文档或 `Content/Python/` 脚本，或文档维度发生变化时更新文档地图 |
| `README.md` | 顶层目录结构代码块（顶层目录变化时）、AI 协作说明（入口机制变化时） |

- 数量必须按实际结果统计，禁止沿用旧数字或凭印象填写。
- 文档描述的实现状态必须与代码真实情况一致，不允许出现文档说"未实现"而代码已存在（或相反）。

## 4. 输出要求

- 回复末尾固定追加「文档同步」小节：列出改动的文档文件与具体改动点。
- 模块相关改动需写明更新了 `README.md` / `<模块>-Dev.md` / `<模块>-Integration.md` 中的哪几份、哪几节；三件套齐全时也说明本次未改哪一份及理由。
- 若本次确实未改变文件或资产结构，写明"本次未改变结构，无需同步文档"并给出依据。
- 若发现 Docs 与实际代码 / 资产已不一致，主动指出并修正文档，不要静默按错误文档执行。

**收尾自检（结构性改动必做）**：出现第 2 节任一判定项时，在收尾运行 `python Content/Python/verify_doc_index.py`（纯 Python 标准库，无需 UE 环境），三项检查——各模块三件套齐全、文档中 `.md` 引用可达、源码分层空 / 非空状态与 `Docs/Source-Structure.md` 目录树一致——全部 PASS 方可收尾；报告写入 `Saved/DocIndexReport/verify.{json,md}`，失败时非零退出，须按报告标签定位断链修复后重跑，并在「文档同步」小节说明校验结果。

## 5. 上下文维护

- **常驻规则**：`.codebuddy/rules/doc-first/RULE.mdc`（`alwaysApply: true`）只做入口导航，不写具体规范，正文保持在 500 行以内；流程变化时同步该规则与本文。规则仅在会话开始时加载，修改后需新建对话才生效。
- `AGENTS.md` 只放稳定信息（项目定位、文档地图、按需拉取协议、硬约束），不写资产总数、文件数等易变数字；数字统一以 `Docs/Content-Structure.md`、`Docs/Source-Structure.md` 文首为准。
- 新增文档时在 `Docs/` 下按单一维度组织，并在 `AGENTS.md` 的文档地图登记"维度 / 覆盖内容 / 何时拉取"。
- **模块文档单一事实来源**：导航 `README.md` 只定义"模块是什么、有哪些文档、已实现什么能力"；`<模块>-Dev.md` 只定义"怎么实现、怎么开发、踩过什么坑"；`<模块>-Integration.md` 只定义"依赖谁、暴露什么接口、别人怎么调用"。同一事实只在一处定义，其余位置用「文档 + 节号」链接。
- **易变数字去重**：资产总数、文件数只写在 `Docs/Content-Structure.md` / `Docs/Source-Structure.md`；模块文档写语义、路径与契约，不复制总数。行为契约中的固定数量（如"4 个原生动作、6 条绑定事件"）可写在导航速查表内，变化时同轮更新。
- **模块文档行数**：单份控制在约 500 行以内，超出时按维度继续拆分，并在模块 `README.md` 的文档清单登记新文档。
- 若项目后续新增 `CODEBUDDY.md`，`AGENTS.md` 将不再自动加载，需在新会话中显式引用 `@AGENTS.md`；因此默认不创建该文件。

## 6. 模块文档制度（固定三件套）

### 6.1 触发与产出

出现以下任一情形必须产出或更新模块文档，缺失视为任务未完成：

| 情形 | 必须产出 / 更新 |
| --- | --- |
| 新建功能模块（源码分层或逻辑资产模块由空变实） | `Docs/<模块>/` 目录 + `README.md` + `<模块>-Dev.md` + `<模块>-Integration.md` |
| 已有模块新增能力，或对外接口、依赖方向、数据流、资产契约变化 | 导航 `README.md` 的能力速查表 + `<模块>-Integration.md` |
| 开发中出现新的坑点 | `<模块>-Dev.md` 的踩坑清单 |

- 模块目录只在进入实现阶段时建立；`Camera/`、`Camera/Modes/` 等预留模块不提前建空目录（`Equipment/` 已进入实现阶段并建立 `Docs/Equipment/`）。
- 模块目录可追加维护文档（如 `<模块>-Validation.md`、`<模块>-Tags.md`），命名以 `<模块>-` 开头，并在 `README.md` 的文档清单中登记，禁止孤儿文档。
- 新建或变更后必须同步 `AGENTS.md` 的「模块文档目录」与文档地图。

### 6.2 固定文件与命名

| 文件 | 固定命名 | 职责 |
| --- | --- | --- |
| 导航 | `Docs/<模块>/README.md` | 模块定位与边界、文档清单与路由、已实现能力速查表、启动与校验入口、维护规则 |
| 开发 | `Docs/<模块>/<模块>-Dev.md` | 实现与经验：源码结构、设计决策、开发 SOP、踩坑清单、校验与冒烟、已知限制 |
| 接口 | `Docs/<模块>/<模块>-Integration.md` | 契约与依赖：模块依赖、数据流、对外接口、调用方式、禁止依赖方向、变更影响面 |

- 三份文档文首固定元信息：`维度 / 模块 / 适用工程 / 最后更新 / 上游规范 / 配套文档`。
- `最后更新` 在每次改动时同轮刷新为当天日期。

### 6.3 各文档固定章节

`README.md`：

1. 模块定位与边界（职责 / 非职责）
2. 文档清单与路由（场景 → 文档 → 章节）
3. 已实现能力速查（动作 / 接口 / 事件 / 回调 / 行为，全模块唯一权威表）
4. 启动与运行时入口（注入位置、绑定位置、关键日志）
5. 未实现能力与扩展方向
6. 校验与报告入口
7. 文档维护规则（改什么要同步哪几处）

`<模块>-Dev.md`：

1. 目的与范围
2. 当前状态与源码结构
3. 设计决策与理由
4. 开发流程 SOP
5. 踩坑清单（现象 / 根因 / 正确做法 / 验证方式）
6. 校验、报告与冒烟
7. 已知限制与后续路线
8. 相关文件

`<模块>-Integration.md`：

1. 模块定位与边界（职责 / 非职责）
2. 模块与外部依赖（`Build.cs` / 配置 / 第三方）
3. 数据流与交互
4. 对外接口（C++ / 资产 / 配置）
5. 其他模块调用方式（顺序 / 前置条件 / 示例）
6. 禁止的依赖方向
7. 变更影响面（改什么要同步谁）
8. 相关文件

### 6.4 踩坑清单写法

每条必须四要素齐全，缺一不成立：

| 要素 | 要求 |
| --- | --- |
| 现象 | 触发条件与可观察结果（报错文本、方向错误、数量不符等） |
| 根因 | 代码 / 资产 / 引擎行为的真实原因，不写"可能" |
| 正确做法 | 具体到文件、函数、资产字段与配置项 |
| 验证方式 | 脚本报告项、日志关键字或 PIE 操作步骤，可复现 |

- 禁止只写"注意 xxx"，禁止把未复现的猜测写进踩坑清单。
- 同一坑点再次出现时，在原条目补充变体，不新开重复条目。

### 6.5 读取协议

1. 进入模块任务 → 先读 `Docs/<模块>/README.md`。
2. 按导航的「文档清单与路由」定位到具体文档与章节，只读相关部分。
3. 仅当导航未覆盖、文档与代码疑似不一致，或需要精确签名时，才定点读源码 / 资产；不做整目录扫描。
4. 发现文档与代码不一致时，以代码为准并在当轮修正文档。

### 6.6 范例

`Docs/Input/` 是首个符合本制度的模块：`README.md` 维护动作与绑定速查表，`Input-Dev.md` 记录开发流程与踩坑，`Input-Integration.md` 记录依赖与接口契约。新增模块直接复制这三份的骨架与写法。
